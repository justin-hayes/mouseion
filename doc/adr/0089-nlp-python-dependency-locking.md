# ADR 0089: Lock and install NLP Python dependencies with uv

Status: **Accepted** · Date: 2026-10-11 · Author: Justin + opencode

Tracked by [issue #1784](https://github.com/justin-hayes/mouseion/issues/1784), under parent [#1776](https://github.com/justin-hayes/mouseion/issues/1776). The implementation ticket follows this decision.

## Context

The NLP service's Python dependencies are declared in two places that agree only by hand:

- `nlp/pyproject.toml` pins the runtime dependencies (`grpcio`, `protobuf`, `stanza`, `transformers`, `huggingface-hub`) and builds the package with setuptools.
- `nlp/requirements-dev.txt` repeats those pins and adds the test and generation tools (`pytest`, `pytest-cov`, `ruff`, `grpcio-tools`, `setuptools`).

Nothing locks transitive dependencies, records hashes, or restricts installs to wheels:

- **CI** (`.github/workflows/ci.yml`) installs `requirements-dev.txt` without a binary-only constraint, installs CPU torch from the PyTorch index, then runs `uv pip install -e nlp`.
- **Sonar coverage** (`.github/workflows/sonarqube.yml`) installs with `--only-binary :all:`, but its torch pin (`torch==2.14.1`) lives in the workflow file, not in a manifest.
- **The NLP image** (`nlp/Dockerfile`) installs CPU torch with `pip`, then `pip install -e ./nlp`. It has no requirements file, so every transitive version floats.
- **Dependabot** watches `/nlp` through the `pip` ecosystem, ignoring `grpcio`, `grpcio-tools`, and `protobuf` as a set.

Sonar reports this as, among others, `text:S8565` (a Python dependency lock file should be committed) and `S8544` (Python dependencies should be locked to verified versions).

The editable install does nothing that the service relies on. Every entry point runs the code from `PYTHONPATH=nlp/src:gen/python`, because the generated `mouseion.v1` bindings in `gen/python` are not part of the package. This covers the image, `compose.yaml`, CI, the Makefile, and `doc/operations.md`. Nothing reads the package's installed metadata, and it declares no entry points.

Resolution probes on this repository, run for this ADR, show the consequences of the current setup:

- **Torch comes with CUDA by default.** Resolving `requirements-dev.txt` without the CPU index selects `torch==2.14.1` with 17 `nvidia-*` wheels plus `triton` on x86_64 Linux, and with `nvidia-*` wheels on aarch64 Linux. `stanza` pulls torch in from PyPI. The CI comment says the CPU-only install prevents the CUDA stack, but the CUDA-capable resolve happens in the earlier dev-requirements step. Whether CI's final environment ends up CPU-only was not verified here.
- **The PyTorch index shadows PyPI when added as an extra index.** `download.pytorch.org/whl/cpu` hosts its own copies of common packages, for example `urllib3 1.26.13` and `requests 2.28.1`. uv prefers an extra index over PyPI, so resolving with `--extra-index-url` for that index picked `urllib3 1.26.13`, while the same dependencies resolved from PyPI picked `2.8.0`.
- **Resolution differs by platform.** The same declared dependencies resolved to `torch==2.10.0` on macOS and `torch==2.14.1` on Linux from PyPI.
- **Binary-only installs are viable for the current set.** All pins have wheels for the probed targets. The binary-only resolve chose the same versions as an unrestricted resolve, so no pin fell back to an older release for lack of a wheel. Details are in [Verification](#verification).

## Decision

### 1. The lock source of truth is `uv.lock`

`nlp/pyproject.toml` declares every direct dependency: runtime dependencies in `[project.dependencies]`, and the test and generation tools in a `dev` dependency group. `nlp/uv.lock`, generated by `uv lock`, is the single resolved, hash-recorded, multi-platform lock. Its per-artifact SHA-256 hashes give integrity without a separate hash-pinned requirements file. Hash-pinned compiled requirements are rejected; see [Alternatives considered](#alternatives-considered).

### 2. `requirements-dev.txt` is retired

The implementation removes `nlp/requirements-dev.txt`. Its pins move into `pyproject.toml`, and everything that installed from it moves to `uv sync`:

- `make setup` uses `uv sync` instead of the requirements file and the separate torch and editable installs.
- CI, the Sonar coverage job, and `make gen` and `make test` use the same `uv sync --locked` install.
- The NLP image installs from the lock.

No second requirements file is kept as an export. The lock is the only resolved artifact.

### 3. CPU-only torch is a locked source, not a side install

`pyproject.toml` declares the PyTorch CPU index as an explicit index and binds `torch` to it:

```toml
[[tool.uv.index]]
name = "pytorch-cpu"
url = "https://download.pytorch.org/whl/cpu"
explicit = true

[tool.uv.sources]
torch = { index = "pytorch-cpu" }
```

`torch` is pinned in `[project.dependencies]` (currently `torch==2.14.1`, the version the Sonar job pins). Because the index is explicit, uv consults it for `torch` only. Every other package, including `urllib3` and `requests`, still resolves from PyPI. No other package can pull torch, and with it the CUDA `nvidia-*` stack, from PyPI.

The lock records CPU torch wheels for Linux x86_64 and aarch64, macOS arm64 (macOS 14 or later), and Windows. The CPU index has no macOS x86_64 wheel for this version, so Intel Macs are not a supported development platform for the NLP service.

The Sonar workflow's torch pin and the lock's torch version must match, so the implementation removes the separate pin from the workflow.

### 4. Binary-only installs, with no exceptions

All dependencies install with `--no-build`, meaning no source distribution is built. The probe showed this works for the full current set (see [Verification](#verification)).

The NLP project is not built either. `pyproject.toml` sets `[tool.uv] package = false`, so `uv sync` installs only the locked dependencies and never builds or installs `mouseion-nlp` itself. The code keeps running from `PYTHONPATH`, as it already does everywhere. This removes the editable install and its build step, and the setuptools build backend is no longer used to build the project. A build backend is not recorded in `uv.lock` and so would otherwise be an unlocked, unhashed input to every install.

Any future third-party dependency that ships only an sdist for Python 3.13 needs an amendment to this ADR, naming the package and the reason, before the lock can include it.

### 5. Install and staleness commands

Commands run from the repository root with `--project nlp`. `UV_PROJECT_ENVIRONMENT` keeps the environment where the Makefile and image expect it, rather than in uv's default `nlp/.venv`. Installs use `--locked`, which fails if `pyproject.toml` and `uv.lock` disagree, and `--no-build`:

```sh
# make setup, CI, and the Sonar coverage job (includes the dev group)
UV_PROJECT_ENVIRONMENT=.venv uv sync --project nlp --locked --no-build --group dev

# NLP image (runtime only), into an environment the image puts on PATH
UV_PROJECT_ENVIRONMENT=/opt/venv uv sync --project nlp --locked --no-build --no-dev
```

CI also runs `uv lock --project nlp --check` whenever `nlp/pyproject.toml` or `nlp/uv.lock` changes. It exits nonzero when the two disagree and tells the author to run `uv lock`. CI's Python path filter and the `setup-uv` cache key move from `nlp/requirements-dev.txt` to `nlp/uv.lock`.

The implementation pins one uv version in the Makefile, in every `setup-uv` step (none pins a version today), and in the NLP image, so that lock output does not change with the installed uv.

### 6. Dependabot moves to the `uv` ecosystem

Dependabot updates `uv.lock` through its dedicated `uv` package ecosystem, not `pip`. The implementation replaces the `pip` entry for `/nlp` with a `uv` entry that keeps the schedule, grouping, commit prefix, and the `grpcio`, `grpcio-tools`, and `protobuf` ignore rules.

Two Dependabot constraints apply:

- **Lock format.** GitHub's supported-ecosystems table lists one supported uv version (v0.11 when this ADR was written). The pinned uv must write a lock that Dependabot can read and regenerate.
- **Both files must move together.** dependabot-core has reported updates that change `uv.lock` without changing `pyproject.toml` ([dependabot-core#12788](https://github.com/dependabot/dependabot-core/issues/12788)). With exact pins in `pyproject.toml`, such a pull request fails `uv lock --check` rather than merging silently.

Manual bumps of `torch`, and of any package held by the ignore rules, edit the pin in `pyproject.toml`, then run `uv lock --project nlp --upgrade-package <name>` followed by `uv lock --project nlp --check`.

## Alternatives considered

- **Hash-pinned requirements compiled from `pyproject.toml`** (`uv pip compile --generate-hashes`, or `pip-tools`). Works with pip and does not require uv in CI. Rejected because it keeps two artifacts that drift apart, needs a per-line index override for torch, and has no native staleness check beyond diffing a regenerated file.
- **Keep the requirements files, add `--only-binary` and `--require-hashes`.** Hashes would have to be generated and maintained by hand on top of the same drift. Rejected.
- **Keep building and installing the project (editable), exempting it from `--no-build`.** Works, as the probe confirmed. Rejected because the install has no consumer, and the build backend stays an unlocked input.
- **Keep the current unlocked installs and document the drift.** Leaves the CUDA stack, index shadowing, and cross-platform torch differences in place, and does not address the Sonar findings. Rejected.

## Consequences

- `nlp/uv.lock` is a new dependency manifest. It should be added to `.github/CODEOWNERS` next to `nlp/pyproject.toml`, as `go.sum` is today. This ADR does not change `CODEOWNERS`; the implementation does.
- `nlp/pyproject.toml`, `nlp/requirements*.txt`, `nlp/Dockerfile`, `.github/` workflows, `.github/dependabot.yml`, and `AGENTS.md` are all CODEOWNERS paths, so the implementation PR needs human review.
- Developer setup instructions change. `AGENTS.md` ("Non-obvious setup"), `doc/development.md` (Dependency updates), and the Makefile describe the requirements-file and `uv pip install -e nlp` flow today.
- `make setup` depends on uv being installed at the pinned version.
- `[build-system]` and `[tool.setuptools]` in `nlp/pyproject.toml` are no longer used to install the service. The implementation decides whether to delete them.
- A future torch upgrade is a `pyproject.toml` change plus a lock regeneration, reviewed as one change.

## Verification

Probes ran on 2026-10-11 with uv 0.13.0 on CPython 3.13.5, against `nlp/requirements-dev.txt`, `nlp/pyproject.toml`, and a prototype `pyproject.toml` carrying decisions 1 to 4. Each probe ran from a scratch copy outside the repository.

| Check | Result |
| --- | --- |
| Binary-only resolve, Linux x86_64 (`manylinux_2_28`) | Resolved, 74 pins from `requirements-dev.txt` and 48 from `pyproject.toml` |
| Binary-only resolve, Linux aarch64 | Resolved, 74 pins |
| Binary-only resolve, macOS arm64, PyPI | Resolved, 55 pins (`torch 2.10.0`) |
| Binary-only versus unrestricted resolve, Linux x86_64 | Identical pins; no version fell back for lack of a wheel |
| Install of the `pyproject.toml` set with `--only-binary :all:` and the CPU index | Succeeded; `torch 2.14.1+cpu`, `grpcio 1.71.2`, `stanza 1.15.0`, `transformers 5.19.0`; zero `nvidia-*` |
| PyTorch CPU index contents | Hosts `urllib3 1.26.13` and `requests 2.28.1`; source of the `urllib3` difference |
| `uv lock` with the explicit CPU torch source | 51 packages, 252 SHA-256 entries, no `nvidia-*`; torch wheels for Linux x86_64 and aarch64, macOS 14 arm64, and Windows, all from the CPU index |
| `uv sync --locked --no-build --group dev`, project packaged, fresh path | Succeeded; uv still built the local project, so `--no-build` does not cover first-party code |
| `uv sync --locked --no-build --group dev` with `package = false` | Succeeded with no build; the 63 NLP tests passed on that environment with `PYTHONPATH=nlp/src:gen/python` |
| `uv sync --project <dir> --locked --no-build --group dev` from outside the project, with `UV_PROJECT_ENVIRONMENT` set | Succeeded; environment created at the given path; `uv lock --project <dir> --check` exit 0 |
| `uv lock --check` on the unchanged lock | Exit 0 |
| `uv lock --check` after adding a dependency, or after setting `package = false` | Exit 1, "run `uv lock`" |

Not verified here, and to confirm in the implementation PR:

- Whether CI's current environment ends up CPU-only or retains the CUDA stack.
- That Dependabot's `uv` ecosystem reads and regenerates a lock written by the pinned uv, and updates `pyproject.toml` with it.
- Which rule `S8541` is, and that the implementation clears all 10 Sonar findings.
