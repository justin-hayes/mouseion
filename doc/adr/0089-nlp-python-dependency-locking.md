# ADR 0089: Lock and install NLP Python dependencies with uv

Status: **Accepted** · Date: 2026-10-11 · Author: Justin + opencode

Tracked by [issue #1784](https://github.com/justin-hayes/mouseion/issues/1784), under parent [#1776](https://github.com/justin-hayes/mouseion/issues/1776). The implementation ticket follows this decision.

## Context

The NLP service's Python dependencies are declared in two places that agree only by hand:

- `nlp/pyproject.toml` pins the runtime dependencies (`grpcio`, `protobuf`, `stanza`, `transformers`, `huggingface-hub`) and builds the package with setuptools.
- `nlp/requirements-dev.txt` repeats those pins and adds the test and generation tools (`pytest`, `pytest-cov`, `ruff`, `grpcio-tools`, `setuptools`).

Nothing locks transitive dependencies, records hashes, or restricts installs to wheels:

- **CI** (`.github/workflows/ci.yml`) installs `requirements-dev.txt` without a binary-only constraint, installs CPU torch from the PyTorch index, then runs `uv pip install -e nlp`.
- **Sonar coverage** (`.github/workflows/sonarqube.yml`) installs with `--only-binary :all:`, but its torch pin (`torch==2.14.1`) lives in the workflow file, not in a manifest.
- **The NLP image** (`nlp/Dockerfile`) installs CPU torch with `pip`, then `pip install -e ./nlp`. It has no requirements file, so every transitive version floats.
- **Dependabot** watches `/nlp` through the `pip` ecosystem, ignoring `grpcio`, `grpcio-tools`, and `protobuf` as a set.

Resolution probes on this repository, run for this ADR, show the consequences:

- **Torch comes with CUDA by default.** Resolving `requirements-dev.txt` without the CPU index selects `torch==2.14.1` with 17 `nvidia-*` wheels plus `triton` on x86_64 Linux, and with `nvidia-*` wheels on aarch64 Linux. `stanza` pulls torch in from PyPI. The CI comment says the CPU-only install prevents the CUDA stack, but the CUDA-capable resolve happens in the earlier dev-requirements step. Whether CI's final environment ends up CPU-only was not verified here.
- **Resolution differs by platform and input.** The same declared dependencies resolved to `torch==2.10.0` on macOS and `torch==2.14.1` on Linux. With the CPU index added, `urllib3` resolved to `1.26.13` from the project metadata and to `2.8.0` from `requirements-dev.txt`. The cause of the `urllib3` difference was not isolated.
- **Binary-only installs are viable for the current set.** All pins in both inputs have wheels for the probed targets. The binary-only resolve chose the same versions as an unrestricted resolve, so no pin fell back to an older release for lack of a wheel. Details are in [Verification](#verification).

## Decision

### 1. The lock source of truth is `uv.lock`

`nlp/pyproject.toml` declares every direct dependency: runtime dependencies in `[project.dependencies]`, and the test and generation tools in a `dev` dependency group. `nlp/uv.lock`, generated by `uv lock`, is the single resolved, hash-recorded, multi-platform lock. Its per-artifact SHA-256 hashes give integrity without a separate hash-pinned requirements file.

Rejected: hash-pinned requirements compiled from `pyproject.toml` (`uv pip compile --generate-hashes`, or `pip-tools`). It would keep two artifacts that drift apart, express the CPU torch index as per-line overrides, and provide no lock-level staleness check beyond diffing a regenerated file.

### 2. `requirements-dev.txt` is retired

The implementation removes `nlp/requirements-dev.txt`. Its pins move into `pyproject.toml`, and everything that installed from it moves to `uv sync`:

- `make setup` uses `uv sync` instead of the requirements file and the separate torch and editable installs.
- CI, the Sonar coverage job, and `make gen` and `make test` use the same `uv sync --locked` install.
- The NLP image installs from the lock.

No second requirements file is kept as an export. The lock is the only resolved artifact.

### 3. CPU-only torch is a locked source, not a side install

`pyproject.toml` declares the PyTorch CPU index as an explicit index and binds `torch` to it:

```toml
[[tool.uv.index]]
name = "pytorch-cpu"
url = "https://download.pytorch.org/whl/cpu"
explicit = true

[tool.uv.sources]
torch = { index = "pytorch-cpu" }
```

`torch` is pinned in `[project.dependencies]` (currently `torch==2.14.1`, the version the Sonar job pins). The explicit index means no other package resolves torch from PyPI, so the CUDA `nvidia-*` stack is not selected. In the probe, the locked install contained `torch 2.14.1+cpu` and zero `nvidia-*` packages. The Sonar workflow's torch pin and the lock's torch version must match, so the implementation removes the separate pin from the workflow.

### 4. Binary-only installs, with one local exception

Locked third-party dependencies install with `--no-build`, meaning no source distributions are built. The probe showed this works for the full current set (see [Verification](#verification)).

The exception is the project itself: `mouseion-nlp` is built from `nlp/src` by its setuptools backend. That is first-party source the repository owns, not a third-party sdist. Any future third-party dependency that ships only an sdist for Python 3.13 needs an amendment to this ADR that names the package and the reason before the lock can include it.

### 5. Install and staleness commands

Environment and image installs use the lock with `--locked` (fail if `pyproject.toml` and `uv.lock` disagree) and `--no-build`:

```sh
# CI and make setup (includes the dev group)
uv sync --locked --no-build --group dev

# NLP image (runtime only)
uv sync --locked --no-build --no-dev
```

CI also runs `uv lock --check` as a separate step. It exits nonzero when `pyproject.toml` changed without a regenerated lock, and the failure message tells the author to run `uv lock`. The implementation pins one uv version in the Makefile and in every `setup-uv` step, which currently pin none, so that lock output does not change with the installed uv. The NLP image installs that same pinned uv before `uv sync`.

### 6. Dependabot and manual bumps

Dependabot's `pip` ecosystem continues to watch `/nlp`, and the `grpcio`, `grpcio-tools`, and `protobuf` ignore rules stay in force. The implementation must confirm that Dependabot's grouped update edits `pyproject.toml` and regenerates `uv.lock` together. If it does not, the implementation must provide another update path before the requirements-file path is removed.

Manual bumps of `torch`, and of any package held by the ignore rules, run `uv lock --upgrade-package <name>` followed by `uv lock --check`.

## Alternatives considered

- **Hash-pinned requirements compiled from `pyproject.toml`.** Works with pip and does not require uv in CI. Rejected because it doubles the manifest, needs a per-line index override for torch, and has no native staleness check.
- **Keep the requirements files, add `--only-binary` and `--require-hashes`.** Hashes would have to be generated and maintained by hand on top of the same drift. Rejected.
- **Keep the current unlocked installs and document the drift.** Leaves the CUDA stack and cross-platform torch differences in place, and does not address the Sonar findings. Rejected.

## Consequences

- `nlp/uv.lock` is a new dependency manifest. It should be added to `.github/CODEOWNERS` next to `nlp/pyproject.toml`, as `go.sum` is today. This ADR does not change `CODEOWNERS`; the implementation does.
- `nlp/pyproject.toml`, `nlp/requirements*.txt`, `nlp/Dockerfile`, and `.github/` workflows are all CODEOWNERS paths, so the implementation PR needs human review.
- The Docker build and CI step names change. `make setup` depends on uv being installed.
- Torch source handling becomes explicit. A future torch upgrade is a `pyproject.toml` change plus a lock regeneration, reviewed as one change.

## Verification

Probes ran on 2026-10-11 with uv 0.13.0 against `nlp/requirements-dev.txt` and `nlp/pyproject.toml`, with the CPU index where stated.

| Check | Result |
| --- | --- |
| Binary-only resolve, Linux x86_64 (`manylinux_2_28`), Python 3.13 | Resolved, 74 pins from `requirements-dev.txt` and 48 from `pyproject.toml` |
| Binary-only resolve, Linux aarch64 | Resolved, 74 pins |
| Binary-only resolve, macOS arm64 | Resolved, 55 pins (default index; `torch 2.10.0`) |
| Binary-only versus unrestricted resolve, Linux x86_64 | Identical pins; no version fell back for lack of a wheel |
| Install of the `pyproject.toml` set on CPython 3.13.5 with `--only-binary :all:` and the CPU index | Succeeded; `torch 2.14.1+cpu`, `grpcio 1.71.2`, `stanza 1.15.0`, `transformers 5.19.0`; zero `nvidia-*` |
| Editable install of `nlp/` with `--only-binary :all:` and with `--no-build` | Both succeeded; the project itself is built |
| `uv lock` from `pyproject.toml` with the explicit CPU torch source | 51 packages, 252 SHA-256 entries, no `nvidia-*` |
| `uv sync --locked --no-build --group dev` on the lock (project not installed) | Succeeded; pytest, ruff, and grpc_tools imported |
| `uv lock --check` on the unchanged lock | Exit 0 |
| `uv lock --check` after adding a new dependency | Exit 1, "run `uv lock`" |

Not verified here, and to confirm in the implementation PR:

- The lock resolves for macOS developers with the explicit CPU index. The probe used the default index on macOS, which selected a different torch. Whether `download.pytorch.org/whl/cpu` serves wheels for macOS was not checked, so the lock may need a platform-specific torch source.
- The `uv sync --locked --no-build --group dev` command with the project included, which the probe skipped.
- Which Sonar rules `text:S8565`, `*:S8541`, and `*:S8544` map to, and whether this decision clears each one.
- Whether Dependabot's grouped pip update regenerates `uv.lock`.
